# Piano v0.9 — file e cartella dal repository, accesso dal browser

> Obiettivo: dal repository si deve poter arrivare al **file** e alla **cartella** — aprire la
> posizione, aprire un file con l'app di sistema, salvarne una copia fuori, copiare il percorso, aprire
> il repository e il commit nel browser. Per gli account, il token deve poter arrivare **dal browser**:
> device flow OAuth (GitHub, GitLab) quando c'è un Client ID, e in ogni caso il pulsante che apre la
> pagina giusta del provider per crearne uno. Ultima modifica: 2026-11-08

## Contesto

-   v0.8 committata (`3367768`, registro `4c7581f`): benvenuto, creazione, clone, account con token in
    memoria (`GIT_ASKPASS`), cartella di base, checkout di un commit.
-   `src/main/index.ts` ha tutti gli handler IPC; `src/shared/api.ts` è il contratto; il preload
    aggiunge il root corrente (`invokeRepo`).
-   Il pannello **File Tree** mostra i file del working tree o di un commit (`state.treePath`,
    `state.selectedCommit`) e ha solo il clic che apre il diff.
-   Il renderer non ha accesso a Node: tutto ciò che tocca il sistema (shell, dialog, lettura file)
    passa da nuovi canali nel main.

## Rischi

-   **Il flusso dal browser richiede un Client ID**: GitHub e GitLab non permettono il device flow
    senza un'applicazione registrata. Il Client ID non è un segreto (viaggia nell'URL) e si può
    salvare nell'account; senza, resta il pulsante che apre la pagina dei token. Va detto
    nell'interfaccia, non scoperto.
-   **`shell.openPath` su file eseguibili**: apre con l'app associata, esattamente come il gestore file.
    Un doppio clic su uno script può eseguirlo: la scelta è dell'utente, ma il menu dice cosa fa.
-   **Salvataggio di file grandi**: tetto di 64 MiB per lettura (`maxBuffer` di `runGit`), oltre si
    ferma con un messaggio invece di troncare in silenzio.
-   **Path**: ogni path del renderer è verificato nel main (`resolveInside`), perché il renderer non è
    una fonte attendibile.

## Esito

Fatto e verificato.

-   **Core**: `src/core/oauth.ts` (device flow GitHub/GitLab, pagina dei token per tutti e quattro i
    provider, corpi `form-urlencoded`, parser di codice/token/utente, `assertClientId`) e
    `remoteWeb`/`commitWebUrl`/`fileWebUrl` in `providers.ts`, con `Account.oauthClientId` normalizzato
    come dato pubblico (una riga sola, o vuoto).
-   **Main**: `src/main/oauth.ts` (avvio, polling con `interval` e `slow_down`, scadenza, annullamento,
    lettura di `GET /user`, salvataggio dell'account) e `src/main/files.ts` (`resolveInside`,
    `readWorkingFile`, `readCommitFile` con `runGitBytes`). Nuovi canali in `src/main/index.ts`, tutti con
    il root esplicito e i percorsi verificati; `app:openExternal` solo http/https.
-   **Renderer**: pulsante *Cartella*, menu della scheda del repository, menu dei file (File Tree ed
    elenco del commit) con doppio clic che apre, voce *Apri il commit nel browser*; nel dialogo account
    il campo Client ID con *Crea…*, *Accedi con il browser*, *Crea un token nel browser…* e l'esito su una
    riga; il campo Client ID sparisce e il pulsante si spegne dove il device flow non esiste.
-   **Verifica**: 130 test (`npm test`), `npm run typecheck`, `npm run build`; prova reale con CDP su
    `/tmp/v09/prova` — copia dal working tree e da un commit precedente identica byte per byte (anche un
    file binario), `../../etc/passwd` e `file://` rifiutati, URL di repository e commit corretti, menu
    attesi, device flow completo contro un GitLab finto su `127.0.0.1:8799` con `authorization_pending`
    al primo giro, account salvato con `oauthClientId` e **senza token** nel file, errore leggibile con
    il provider spento.
-   **Resta aperto** (in `TODO.md`): albero completo del repository (oggi le azioni valgono sui file
    modificati e sui file di un commit), salvataggio di una cartella intera o di uno zip, link web ai file
    per Gitea, un Client ID predefinito per GitHub così l'accesso dal browser funziona senza registrare
    un'applicazione.
